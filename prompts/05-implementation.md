# S5 代码实现与基线复现

> 目标：搭好实验代码骨架，**先把基线复现对齐，再实现自己的方法 v1**。顺序不可颠倒——没有可信的基线，之后所有对比都是空中楼阁。

## 1. 代码骨架

```
src/
  data/         # 数据下载、预处理、划分（幂等脚本）
  methods/      # baselines/ 与 ours/ 分开；共享接口
  eval/         # 唯一的评测入口——所有方法共用同一份评测代码
  utils/
configs/        # 每个实验一份 yaml，配置即文档
scripts/        # run_experiment.py：读 config → 跑 → 输出到 EXPERIMENTS/exp-XXX/
```

工程铁律：
- **评测代码只有一份**，任何方法不得自带评测逻辑（自评自测是数字造假的温床）。
- 配置全部显式：种子、版本、超参写进 config.yaml，运行时把 config 快照 + `git rev-parse HEAD` + `pip freeze` 存入实验目录。
- 结果落盘为机器可读（json/csv），`RESULTS.md` 由脚本从原始输出生成，**不手填数字**。
- 先写数据与评测的单元测试（对拍几个手算样例），再跑任何实验。

## 2. 基线复现流程（E1）

1. 优先用官方代码；无官方代码时找星数最高的第三方复现，并在日志记录出处。
2. E0 冒烟通过后跑完整基线，与原论文数字对照：
   - 差距 ≤1 点：通过，锁定该配置为 frozen baseline;
   - 差距 >1 点：进入排查清单——数据版本？预处理差异？评测细节（大小写/截断/平均方式）？超参？依赖版本？逐项排除并记录；
   - 排查后仍无法对齐：在 `RESEARCH_LOG.md` 记录差距与最可能原因，**用统一评测协议下的自测数字做后续对比**（论文中如实说明），绝不引用自己复现不出的数字。
3. 每个基线完成后立即写 `report.md` 并提交 git。

## 3. 方法 v1 实现（E2）

- 严格按 `PROPOSAL.md` 的方法草图实现**最简版本**：先让核心机制跑起来，抵制一切"顺手加个改进"的冲动——那些留给 S6，一次一个地加，否则说不清楚增益来自哪。
- 与基线共享一切可共享的代码路径（数据、评测、训练循环），差异只存在于 `methods/ours/`，保证对比公平。
- v1 跑完与基线对比，无论结果好坏，写入 report 与 `RESEARCH_LOG.md`：
  - v1 就超基线：好信号，进 S6 继续放大优势；
  - v1 持平或更差：**正常现象**（首版通常如此），进 S6 用误差分析找原因，不要恐慌也不要在本阶段乱调。

## 4. 出口

基线复现全部对齐（或差距已记录在案）+ 方法 v1 有完整对比数字 → 更新 `RESEARCH_LOG.md`，进入 S6。
